# Independent architectural tick width: reference preparation

LC-MON-001 requires dimension tick thickness to be independently controllable
without changing tick centerlines, dimension-line thickness or extension-line
thickness. The current beta2 renderer and plotter use one stroke treatment for
all those dimension segments. No independent width has been implemented yet.

The remaining domain decision is whether the new width represents model-space
geometry that scales with the viewport or a fixed physical thickness on paper.
Existing intake establishes an independent width at one scale; that observation
alone cannot choose behavior at another scale. No measured value is a new global
default. Until this choice is resolved, the issue is `needs-domain-review`.

## Synthetic reference

`tests/tick-width-fixture.mjs` is independently authored, contains no client
geometry, and does not insert any proposed width property into the drawing.
It contains one 1000 mm horizontal linear dimension and two saved locked Top
viewports on a 420 by 297 mm sheet. Dimension/extension lineweight is 0.1 mm.
Tick size is 25 model mm; endpoints are literal, rather than generated by the
production geometry routine.

| Viewport | Proposed 12 mm model width | Proposed fixed 0.24 mm paper width |
|---|---:|---:|
| 1:50 | 0.24 mm | 0.24 mm |
| 1:100 | 0.12 mm | 0.24 mm |

These are two alternative acceptance policies, not two implemented settings.
The second viewport makes a mistaken constant/scaled interpretation observable.
In both alternatives ordinary dimension and extension strokes must remain 0.1 mm,
and all centerline endpoints and lengths must remain unchanged.

Run the focused reference checks with:

```
node --test tests/tick-width-reference.test.mjs
```

The four checks establish independent arithmetic, literal model endpoints,
literal paper projections and complete legacy native serialization. Passing
them does not mean that independent tick width is supported. They are a foundation
for the later failing regression, not a replacement for it or a new candidate gate.

An actual baseline PDF was also produced by the unchanged beta2 production plot
service in isolated hidden Chromium. Independent vector reading matched all ten
tick/dimension/extension segments across both viewports. All measured widths were
approximately 0.09999931 mm, confirming the existing shared 0.1 mm treatment.
The new reader uses a 0.005 mm width bound and the existing 0.04 mm endpoint /
0.02 mm length bounds; missing-tick, wrong-width and doubled-length negative
controls were rejected. The actual render was visually inspected. This is a
hidden source plotting diagnostic, not native UI or new-feature acceptance.
Its initial restricted-shell launch failed before output; one authorized isolated
launch succeeded. Both attempts and the private evidence remain preserved.

## Implementation acceptance after the decision

Add a focused failing regression for the selected width policy, then a minimal
implementation. Check validation, atomic style updates, complete Undo/Redo,
native Save/reopen, unchanged unset/legacy behavior and actual PDF stroke widths
at both viewport scales. The independent PDF reader must match literal endpoints
and measure tick and body strokes separately; negative controls must reject
missing ticks, inherited body width, changed body width and incorrect tick length.

Preserve the old candidate/manifests and exact beta2 native evidence. Any later
runtime change needs a distinct reviewed identity. New optional width data may
be discarded by older readers, and exchange support requires explicit checks;
do not imply complete backward or DXF compatibility from native persistence.
Leader ticks are a separate scope. No installer or client drawing is part of
this reference-preparation work.

## Policy selected - October 25, 2026

The user selected width that scales with the viewport, matching the recorded
reference. The earlier pending-policy paragraphs are preparation history. See
[TICK-WIDTH-IMPLEMENTATION.md](TICK-WIDTH-IMPLEMENTATION.md) for the optional
style field, annotation-scale behavior, compatibility limits and candidate scope.
